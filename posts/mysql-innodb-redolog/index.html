Mysql-InnoDB redolog的设计与实现

发表于2026-03-12|更新于2026-04-27|Tech
|总字数:3.8k|阅读时长:12分钟

一、前情提要

  • 数据的组织方式
  • 单个页面的结构

二、Buffer Pool

在Mysql服务器启动时会向操作系统申请一片连续的内存，作为连通cpu和磁盘的桥梁，加快读写速度。

1. Buffer Pool的组成

  • 控制块
    控制块和缓存页是一一对应的关系，里面包含对应缓存页的所属表空间编号、页号、缓冲页在Buffer Pool中的地址、链表节点信息等等

  • 缓存页
    数据在InnoDB中的存储方式都是以页为单位存储的，默认16KB大小，这里也是一样的

  • 碎片
    由于控制块的大小是不固定的「比如DEBUG模式下占用缓冲页大小的5%左右，非DEBUG模式下更小一些」，很难将Buffer Pool的大小设置为控制块加缓存页的整数倍，那么最后剩余的空间不足以再分配一对控制块和缓冲页，就会成为内存碎片

2. 组织方式

  • free链表
    当从磁盘上读取一个新数据页时，需要判断是否还存在空闲的缓存页可以使用，空闲的缓冲页的组织方式就是链表，链表中的节点并不是缓冲页而是记录着缓冲页地址的控制块

读取一个数据页的时候，判断该数据页是否已经存在Buffer Pool中的方法是通过哈希表的方式进行快速定位的，key=表空间号+页号，value=控制块的地址

  • flush链表
    当修改了Buffer Pool中某个缓冲页的数据时，将导致它与磁盘上的数据不一致了，此类缓冲页称脏页「每次修改缓冲页都同步到磁盘上会带来比较大的性能损失，通常是异步刷盘」，flush链表就是用来记录着脏页的
  • LRU链表
    由于Buffer Pool的内存大小是有限的，一旦free链表不存在空闲的缓冲页，那么最新读取的数据页将得不到分配。为了解决该情况，Mysql使用LRU策略对缓冲页进行回收

1. 简单的LRU链表
如果访问的数据页不在Buffer Pool中，那么就从磁盘中加载进来，同时将对应的控制块放到LRU链表的头部；如果访问的数据页在Buffer Pool中，只需要将对应的控制块放到LRU链表的头部

两种特殊情况：

  1. InnoDB提供了预读功能，即读取了某个页面之后，可能会将后面的页面也一并预加载到Buffer Pool中。如果预读进来的页面基本没有用到，而且处于LRU尾部的缓冲页很快就会被淘汰掉，那么将会大大降低Buffer Pool的命中率
  2. 在执行全表扫描sql语句的时候，需要把访问到的所有数据页加载到Buffer Pool中，可能会排挤出大量原有的缓冲页，甚至直接‘清仓’，然后其他语句执行的时候又需要重新加载进来。因为全表扫描的频率一般不会太高，这样也会大大降低Buffer Pool的命中率

2. 划分区域的LRU链表
  鉴于以上两种特殊情况，InnoDB重新设计了LRU链表。一部分存储使用高频的缓冲页，简称young区域；一部分存储使用低频的缓冲页，简称old区域
     

针对情况1，InnoDB规定，当某个页面初次加载到Buffer Pool中，该缓冲页会放到old区域的头部，这样就不会影响到高频访问的young区域

针对情况2，全表扫描的时候确实会用到每条记录，所以每次访问一条记录，都代表访问一次页面，那么页面将在后续的访问中会从old区域移到Buffer Pool的young区域头部，这样也会造成将之前的高频缓冲页全部排挤出去。所以InnoDB规定对某个页面的访问时间和第一次的访问时间在某个时间间隔中「默认1s」，那么就不会从old区域移动到young区域头部

进一步的优化：
对于young区域的缓冲页定位是高频访问区域，那么每次访问一个缓冲页都需要将其放到young区域的头部，为了降低频繁的移动操作，InnoDB也规定了处于前1/4young区域的缓冲页无需移动到young头部

3. 多个Buffer Pool实例

在多线程环境下，访问单一的Buffer Pool是需要加锁的，那么为了提高多线程的处理速度，将Buffer Pool拆成了多个分布到多个实例。此外，在Mysql5.7之后，是允许调整Buffer Pool的大小的，每次的调整都需要申请一块更大的内存空间，然后将旧数据复制过来，是非常耗时的。所以单个实例的Buffer Pool又被拆分为多个chunk，以chunk为单位对Buffer Pool进行扩充

三、 redo log

InnoDB是以页为单位进行磁盘IO的，修改一个字节的内容就把整个页去落盘十分浪费；此外，一次事务可能修改了多个页面，落盘都需要多次随机IO，速度也会十分缓慢。所以，为了保证对数据做出修改的相对持久性，InnoDB将对数据做出的修改以redo log的形式顺序写入磁盘中。遇到因系统崩溃而重启时，可以某一起点按照redo log的顺序重新更新一下数据页即可「redo log完全是按照修改页面的顺序去写入的，所以不同事物的产生的redo log是可以交叉写入的」

1. 结构定义

  • Type1
    即redo log的类型，比如MLOG_1BYTE、MLOG_2BYTE、MLOG_COMP_REC_INSERT、MLOG_COMP_REC_DELETE等类型

单次操作在某个页面的某个偏移量的位置修改了1个字节，那么就会记录一条MLOG_1BYTE类型的redo log。但是对数据库的操作往往不会这么简单，更多的是会引起多个页面的修改，比如我们插入一条记录记录了一条MLOG_COMP_REC_INSERT类型的记录，不仅会涉及叶子结点页面的修改，上层的目录项页面和记录统计数据的页面都需要修改。在利用redo log进行数据恢复的时候，不单单是对redo log记录页面位置的直接恢复，同时也会调用一些函数，将受到该条redo log影响的页面其他位置进行间接恢复。

  • Space ID、Page Number、Data**

    即表空间ID、页号、实际数据

具象的展示一条redo log，比如一条MLOG_COMP_REC_INSERT类型的redo log

  • 日志组
    在对数据库进行修改操作中，会产生非常多的redo log，而有些redo log是要求必须绑定到一起的，需要一起写入到log文件中，保证原子性。这样一组的redo log对底层页面的一次原子访问过程称为一个Mini-Transaction，简称MTR

比如一次insert操作：更新MAX ROW ID属性时产生的redo log为一组；向聚簇索引中的B+树中的页面插入一条记录时产生的redo log为一组；向某个二级索引中的B+树中的页面插入一条记录时产生的redo log为一组；等等…….

如果是一组redo log记录，会有一条类型为MLOG_MULTI_REC_END的redo log标志结束

如果只是单独一条redo log为一组，那么会在type字段的第一个bit位记1

2. 写入过程

为了更好地管理redo log，InnoDB将redo log放到512字节的block中存储

为什么在block最后有一个校验值：
因为在一个block在写到一半的时候宕机了，那么在崩溃恢复读取redo log的时候，导致在读取到该block校验值的时候发现和利用header+body计算出来的校验值是不一致的，就会直接终止

  • redo log buffer
    为了提高写入redo log时与磁盘的交互效率，InnoDB申请了一段连续的内存作为redo log的缓存区，每次写入也是按照一组MTR为单位进行写入的。通过启动选项Innodb_log_buffer_size指定redo log buffer的大小

redo log buffer的刷盘时机：

  • redo log buffer空间不足

  • 事务提交的时候

  • 将某个脏页刷新到磁盘前需要确保缓存中的redo log刷入磁盘，为了保证redo log的写入的顺序性，该脏页对应缓存中的redo log之前的也要刷入磁盘中

  • 后台有一个定时线程将缓存中的redo log落盘

  • 正常关闭服务器

  • 做checkpoint时

  • redo log文件组
    redo log落到磁盘中的文件默认是有两个的，每个48M大小。可以通过innodb_log_files_in_group和innodb_log_file_size指定文件的个数和大小。可以看出redo log分配的磁盘存储空间是有限的，所以说redo log都是在循环利用这有限的空间，即循环写入

redo log的文件格式和redo log buffer一样，只不过在每个redo log文件的前4个block是需要记特殊信息的，也就是从512 * 4=2048处开始记录真正的redo log，放到普通的block中

属性名 长度(单位:字节) 描述
LOG_HEADER_FORMAT 4 redo 日志的版本，在 MySQL 5.7.21 中该值永远为1
LOG_HEADER_PAD1 4 做字节填充用的，没什么实际意义，忽略~
LOG_HEADER_START_LSN 8 标记本 redo 日志文件开始的LSN值，也就是文件偏移量为2048字节初对应的 LSN值
LOG_HEADER_CREATOR 32 一个字符串， 标记本 redo 日志文件的创建者是谁。正常运行时该值为 MySQL 的版本号，比如: “MySQL 5.7.21” ，使用mysqlbackup 命令创建的 redo 日志文件的该值为 “ibbackup” 和创建时间
LOG_BLOCK_CHECKSUM 4 本 block的校验值，所有block都有
checkpoint2字段含义「checkpoint1和其同结构」:
属性名 长度(单位:字节) 描述
LOG_CHECKPOINT_NO 8 服务器做 checkpoint 的编号，每做 一次 checkpoint ，该值就加1
LOG_CHECKPOINT_LSN 8 服务器做 checkpoint 结束时对应的 LSN 值，系统崩溃恢复时将从该值开始
LOG_CHECKPOINT_OFFSET 8 上个属性中的 LSN 值在 redo 日志文件组中的偏移量
LOG_CHECKPOINT_LOG_BUF_SIZE 8 服务器在做 checkpoint 操作时对应的 log buffer 的大小
LOG_BLOCK_CHECKSUM 4 本block的校验值，所有block都有

实际上记录checkpoint信息的只有第一个文件，可能是为了redo log文件结构的统一性，其他文件也都存在checkpoint这一类block

3. log sequence number(LSN)

自Mysql服务器启动，就在不断地生成redo log，而LSN就是用来记录总共生成的redo log的字节数，默认初始值为8704「InnoDB作者自定义的初始值」。在初始化redo log buffer的时候，由于每个block的header默认占用12字节，所以LSN=8716

示例：比如第一组事务依次产生了三组MTR，大小分别为200字节、1000字节和52字节

LSN增长过程：

  • 初始LSN=8716
  • 写入第一组MTR_1，LSN=8916
  • 写入第二组MTR_2，LSN=8916+1000+42+122=9948
  • 写入第三组MTR_3，LSN=9948+52=10000

Buffer Pool与LSN的联系
在Buffer Pool中的flush链表是由控制块组成的，每一个控制块内其实还有两个字段记录着关于LSN的信息：

  • oldest_modification，记录着第一次修改Buffer Pool中的缓冲页时，将修改该页面的MTR开始前的LSN写入到该字段
  • newest_modification，每次修改一次页面，都会将修改该页面的MTR结束时对应的LSN写入到该字段

继续使用上面写入三组MTR的例子，假设MTR_1修改了页面a，MTR_2修改了页面b和页面c，MTR_3修改了页面b和页面d，之后形成的flush链表如下「o_m、n_m分别为以上两个字段缩写」

可以看到flush链表中的节点是按照o_m的顺序递减排序的，后续对重复页面的更新只会更新n_m的值

Checkpoint
前面说过redo log file是有限的，循环利用需要判断那些日志能够覆盖，而checkpoint就是来解决这个问题的，每次checkpoint都将得到一个变量checkpoint_lsn。分为两个步骤：

  • 计算当前可以被覆盖的最大LSN的值checkpoint_lsn，redo log能够被覆盖的理由一定是它所修改的页面已落入磁盘持久化，也就是在flush链表尾结点的o_m对应的值，
  • 将checkpoint_lsn存入前面所提到的redo log文件组的第一个文件中的checkpoint类的block中，同时更新其中的checkpoint_no和checkpoint_offset「此处对于存入checkpoint1还是存入checkpoint2中依据checkpoint_no的奇偶性」

崩溃恢复

1. 确定恢复的起点
前面在进行checkpoint操作的时候，得到的值存入了redo log文件组的第一个文件中，小于该值的redo log是可以覆盖掉的也就表示失去作用了，而不小于该值的redo log可能需要我们拿来恢复数据。

flush链表的刷盘动作不一定都是从链表尾结点开始的，比如将使用率最低的页面刷盘，也就是将LRU链表的尾结点对应的页面刷盘，而该页面不一定是flush链表尾结点对应的页面，也就是flush链表的中间节点对应的页面可能已经刷盘了
所以说对于不小于checkpoint_lsn的redo log，对应的页面可能已经刷盘了，这种情况其实是可以跳过的。newest_modification就是来协助做这件事的，在进行flush链表节点对应的页面刷盘时，会将节点中的newest_modification的值一起存入页面的header中FIL_PAGE_LSN字段中。这样在利用redo log找到待恢复页面的时候，先读取FIL_PAGE_LSN字段的值，判断大于checkpoint_lsn就表明该页已经落入磁盘了

2. 确定恢复的终点
  普通block的 log block header 部分有一个叫做 LOG_BLOCK_HDR_DATA_LEN 的属性，该属性值记录了当前block 里使用了多少字节的空间。对于被填满的block来说，该值永远为 512 。如果该属性的值不为 512 ，那么它就是此次崩溃恢复中需要扫描的最后一个block

3. 加快恢复
  利用哈希表，将记录着相同space ID和page number的redo log放到同一个槽中，按照生成的先后顺序排序

如果一次事务的redo log已经写入磁盘，在事务执行到一半突然宕机了，那么下次重启进行崩溃恢复不就会拿到脏数据吗，违背原子性
利用undo log的回滚特性解决，在Mysql的某个页面存储着全局的活跃事务，在崩溃恢复的时候如果发现某个事务处于活跃状态，那么也就表示该事务之前并没有完成，将其做的修改回滚掉即可
