2. 存储方式

在InnoDB中，记录数据的行格式有多种，有compact、redundant、dynamic、compressed四种，这里着重介绍compact行格式，其他大同小异。

记录的额外信息:

  • 变长字段宽度列表
    针对一些长度可变的数据类型（varchar、varbinary、text）的实际长度存储，按列逆序存储
    第一条记录的该字段存储方式是‘0x01，0x03，0x04’ 分别对应c4，c2，c1
    第二条记录的该字段存储方式是‘0x03，0x04’分别对应c2，c1。null值不存储

如何确定需要用几个字节存储某类型的长度
假设varchar(M)类型，根据建表所使用的字符编码类型确定单字符最大占用字节数量W（比如ascii：W=1，gbk：W=2，utf8(utf8mb3)：W=3），实际占用的字节数量L

  • M*W<=255 ，使用一个字节存储长度（和示例相同）
  • M*W>255
    • L<=127，使用一个字节存储，首位置0
    • L>127，使用两个字节存储，首位置1

还有一点，如果使用的字符编码类型是可变类型，那么即便使用的char(M)类型，也会被写入到该字段中

  • null值列表
    针对每一个可以为null的列都会对应一个二进制位，按列逆序存储
    第一条记录的该字段存储方式是‘0b00000000’，分别对应c4，c3，c1
    第二条记录的该字段存储方式是‘0b00000110’，分别对应c4，c3，c1

  • 记录头信息（占用5个字节，前两位bit预留未用）

delete_flag：占用1bit，软删除标志位
min_rec_flag：占用1bit，B+树的每层非叶子节点中最小的目录项记录标志位
n_owned：占用4bit，在innodb中一个页面的记录会被分为若干个组，每个组都有一个”带头大 哥“，其余的都是”小弟“。”带头大哥“记录的n_owned 代表着该组中所有记录的条数，”小弟“的 n_owned 都为0
heap_no：占用13bit，表示当前记录在页面堆中的相对位置编号
record_type：占用3bit，表示记录的类型（0表示普通记录，1表示B+树中非叶子节点中的记录， 2表示Infimum，3表示Supremum）
next_record：占用16bit，表示下一条记录的相对位置

记录的真实数据：

  • row_id：如果建表时没有指定主键，并且表中又找不出非空且唯一的列的话，那么MySQL会自动为该表生成一个隐藏的有序的列作为主键列，这个列就是row_id，用6个字节表示（所以该ID能表示的范围就是1 ~ 2 ^48 ）
  • transaction_id：记录着最近修改这条数据的事务ID
  • roll_pointer：回滚指针，主要是为innodb的mvcc生成版本链使用
  • 剩下的部分就是对真实数据的存储了

2. InnoDB数据页格式

InnoDB的数据页大小一般是16KB的，存储方式如下：

  • Infimum和Supremum
    Infimum和Supremum分别为页中的最小记录和最大记录，每条记录都是5字节额外信息和8字节单词拼写共13字节，起到哨兵的作用
  • User Record（图中的delete_flg=delete_mask、min_rec_flag=min_rec_mask）
    实际上有序的记录不一定能够存储在连续的内存空间中，主要依靠记录头信息中的next_record字段，可以抵达下一条记录的真实数据的起始位置，这样向右就是真实数据，向左就是该条记录的额外信息（而变长字段长度列表、null值列表刚好是逆序存储）。
  • Page Directory
    InnoDB是会给包括Infimum和Supremum在内的记录进行分组的，Infimum自成一组，Supremum最多拥有8条记录，其余都在4-8条，也就是前面说的组内‘老大’的记录头信息中的n_owned字段的值。而组内的‘老大’的的真实数据的起始点在页内的位置作为一个槽位放入Page Directory存储起来。

为什么要放到Page Directory中
假设继续插入12条数据，目前的主键id增到16，如下图。 比如想要找到主键id=6的记录，那么就可以在Page Directory使用二分法快速定位id=6所在记录的位置。采用分组的形式而没有记录所有地址可能是为了节省空间。

  • File Header
  • Page Header
  • File Trailer
    占用8个字节，前4个字节表示校验和，和File Header的FILE_PAGE_SPACE_OR_CHKSUM字段呼应。需要在将整页刷新至磁盘的时候，需要计算整页的校验和，只有当头尾的校验和一致才表示整页写入磁盘；后4个字节与FILE_PAGE_SPACE_OR_CHKSUM的后4个字节进行对比，校验完整性

比如在机器宕机或者停电的情况下，整个16KB大小的页面只有前半部分写入磁盘，那么可以对比File Header和File Trailer的校验和检测出来

三、 多个页面构建成树

1. 目录项（非叶子节点）

叶子节点存储用户的真实记录，而目录项的用户记录只有两列，主键id和页号。页号是指向的下一层级的某个页面编号（File Header中FILE_PAGE_OFFSET），主键id是某个页面的最小主键id值。

这里依旧使用上面的那张表t2，插入若干条数据，假设一页最多存储4条用户记录，形成如下树状结构。记录与记录之间采用next_record连接形成单向链表，同层级的页与页之间采用File Header中的FILE_PAGE_PREV和FIEL_PAGE_NEXT两个字段连接形成双向链表（页号可以不连续）。

在二级索引形成的B+树中的非叶子结点存储的用户记录由索引值、主键id组成，当索引值一样那么会根据主键id作比较

2. 索引的代价

  • 空间成本
    这一点是显而易见的，每建立一个索引都会为它搭建一颗B+树
  • 时间成本
    • 每次的增删改操作，可能会对节点和记录的排序造成破坏，需要额外的时间去做页面之间和页面内记录的调整
    • 在执行查询语句之前，首先要生成一个执行计划，会根据查询语句中的条件选取最优的索引方案，如果索引过多，也会增加分析成本的耗时
  • 更好的创建和使用索引
    • 只为用于搜索、排序或分组的列创建索引
    • 考虑索引列中不重复值的占比
    • 索引列的类型尽量小（有时可以采用列前缀建立索引）
    • 减少回表，使用覆盖索引
    • 让索引列以列名的形式在搜索条件中出现
    • 避免冗余和重复索引

四、多棵树的组织方式-表空间

1. 落入磁盘

每次执行‘create database table_name;’新建数据库时就会在mysql的数据目录的文件路径下新建一个子目录。

每次执行‘create table table_name(c1 int);’时就会在子目录下新建一个table_name.frm文件，用来描述表的结构，写入数据会创建另一个名为table_name.ibd的文件用于存储用户数据。

2. 独立表空间结构

InnoDB有多种表空间，这里主要介绍独立表空间「也是mysql5.6之后默认的表空间」

基本概念：

为了更好地关联表空间中的页，采用了分区和分组的概念

  • 区（extent）：连续的64个页就是一个区，大小就是64*16KB=1MB
  • 组：连续的256个区划分为一组
  • 段：一颗B+树索引会分为两个段，一部分存储叶子节点的区的集合，另一部分存储非叶子节点的区的集合

为什么出现区的概念
当需要获取大量记录时，单纯通过页与页之间行的双向链表去遍历，由于页号不一定是连续的，跳跃性可能会非常大，造成多次磁盘随机io。所以后续采用以区为单位分配空间，而区是由的是连续的64个页组成，这样能够更大概率的使用顺序io，缺点是可能造成空间浪费

在File Header中的FILE_PAGE_TYPE字段表示页的类型，前面所说的B+树上的页面都数属于FILE_PAGE_INDEX类型
上图中可以看到每一个组的第一个分区前三个页面类型是有一些不一样的：

  • 第一个页面类型是FILE_PAGE_TYPE_FSP_HDR类型，用来记录整个表空间的一些整体属性一级本组内所有区的属性
  • 第二个页面类型是FILE_PAGE_IBUF_BITMAP，用来存储change buffer的一些信息
  • 第三个页面类型是FILE_PAGE_INODE，用来存储INODE Entry结构体

FILE_PAGE_TYPE的枚举值也还有很多其他类型如下图所示

组织方式：

  • 区的状态
    • 空闲的区FREE：还没有用到该区的任何页面
    • 有剩余空间的碎片区FREE_FRAG：表示碎片区还有可以被分配的空闲页面
    • 没有有剩余空间的碎片区FULL_FRAG
    • 附属于某个段的区FSEG

碎片区出现的原因：在以区为单位为段分配空间的时候，如果数据量非常小，根本用不到64个页面这么大的空间，就可以先放到碎片区中存储，碎片区属于不同段的公共空间

  • 区的数据结构EDES Entry
  • Segment ID：区所属的段id
  • List Node：用于将区串联起来，形成双向链表，共计三种（表空间维度）
    • 归属于表空间的三个链表
      • FREE链表：将FREE状态的区串联起来
      • FREE_FRAG链表：同上
      • FULL_FRAG链表：同上
    • 归属于段的三个链表
      • FREE链表：区的状态是附属于段，且所有页面空闲
      • NOT_FULL链表：区的状态是附属于段，且部分页面空闲
      • FULL链表：区的状态是附属于段，且无页面空闲
  • state：即前面说的区的状态
  • Page State Bitmap：共计16*8=128位，而区内包含64个页，所以每个页占两位，第一位表示该页是否空闲，第二位为预留位
  • 段的数据结构INODE entry
  • Segment ID：表示段id
  • NOT_FULL_N_USE：表示前面提到的NOT_FULL链表的已用页面数量
  • 3个List Base Node分别记录了归属于段的三个链表的头节点和尾节点
  • Magic Number：无特殊含义
  • Fragment Array Entry：因为段内数据不一定只会落到归属于段的区上，也可能落到碎片区中，这里记录了使用到的多个碎片区的信息

页面类型：

  • FILE_PAGE_TYPE_FSP_HDR页面类型
  • File Space Header：存储的是表空间的一些整体属性信息，比如前面说的归属于表空间的三个链表的基节点的List Base Node结构，还有后面即将提到的两个链表基节点结构
  • XDES Entry 0-255：表示组内的256个区的结构体

分组的原因
当数据量比较大时，一个页面是无法存储所有区的XDES Entry结构的，所以分为了若干个组进行管理

  • FILE_PAGE_TYPE_XDES页面类型
    作为表空间的非第一组的第一个区的第一个页面，他的结构和FILE_PAGE_TYPE_FSP_HDR类似，去掉了File Space Header
  • FILE_PAGE_INODE类型页面

这个页面的主要作用就是用来存储前面提到的段的结构INODE Entry

  • List Node for INODE Page List：可以看出这个页面最多存储85个段结构，为了兼容超过85个情况，涉及的链表结构，将表空间内的存储段结构的页面串联起来，形成两类双向链表。此外，这两个链表的基节点会被放入到FILE_PAGE_TYPE_FSP_HDR页面中的File Space Header中
    • SEG_INODE_FULL链表：已经没有空闲空间来存储INODE_Entry结构
    • SEG_INODE_FREE链表：还有空闲空间来存储INODE_Entry结构
  • INODE Entry0-84：表示被存入该页面的段的结构

如何利用数据页面反查段的INODE Entry结构的存储位置
在FILE_PAGE_INDEX类型的页面中，在Page Header中是有记录的，分别为

  • PAGE_BTR_SEG_LEFT：记录了叶子节点段的INODE_Entry位置
  • PAGE_BTR_SEG_TOP：记录了非叶子节点段的INODE_Entry位置
    因为每一颗B+树都会有两个段（叶子节点段和非叶子节点段），所以只需要在B+树中的根节点页面记录该信息即可
